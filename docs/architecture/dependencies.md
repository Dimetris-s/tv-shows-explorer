# Направление зависимостей

## Зависимость — это импорт

`A` импортирует `B`, значит, `A` зависит от `B`: изменение `B` может потребовать правок в `A`. Циклы (`A → B → A`) запрещены (`import/no-cycle`): в цикле любое изменение задевает всех участников.

## Главное правило

**То, что меняется часто, зависит от того, что меняется редко.** От часто меняющегося кода никто не должен зависеть.

Отображение меняется чаще бизнес-логики: один и тот же сценарий можно нарисовать сотней способов, а новый сценарий всё равно требует нового интерфейса. Поэтому отображение зависит от бизнес-логики, а не наоборот.

```
отображение                     бизнес-логика
View → Presenter  ───────────→  Tasks → Stores
```

Так получается из коробки, без дополнительных паттернов. Линтер следит за направлением: `front-layers`, `server-layers`, `framework-free-tasks` (`enforcement.md`).

## Уровень модуля

Уровень модуля определяется **расстоянием до ввода-вывода** (экран, сеть, база), а не тем, кто кого вызывает. Чем дальше от ввода-вывода, тем выше уровень и тем стабильнее код.

- Презентер ближе к экрану, чем таска, поэтому он ниже. Связь «презентер импортирует таску» **уже направлена правильно**, инверсия здесь не нужна.
- Интерфейс таски описывает **вариант использования**, а не нужды конкретного экрана. Таска принимает минимум необходимого и возвращает данные в терминах предметной области. Переводить их в подписи, флаги и состояния экрана — работа презентера.
- Проверка: сможет ли другой клиент (другой экран, мобильное приложение, бот) вызвать таску как есть? Если таска возвращает `label`, `isEmpty` или `kind` экрана, в бизнес-логику протёк UI.

## Инверсия зависимостей (DIP)

Инверсия нужна там, где обычный порядок вызовов заставил бы стабильный код зависеть от нестабильной детали: таске нужны сокеты, конкретная библиотека, внешний API. Стабильная сторона объявляет нужный ей интерфейс, деталь под него подстраивается. Замена детали (socket.io → SSE) затрагивает только модуль-адаптер.

В проекте:

- **Сервер ↔ TVmaze.** Серверная сетевая таска переводит DTO TVmaze в наш `Show`. Остальной сервер про TVmaze не знает.
- **Фронт ↔ сервер.** Оба зависят от контракта (`@tv/server/contract`), а не друг от друга. Фронт не импортирует серверный код, только типы контракта.
- **Таска ↔ `services/http`.** Таска знает транспорт напрямую: осознанное решение без DAL (`tasks.md`). Смена транспорта затрагивает `services/http`.

## Узкие интерфейсы

Между View и презентером, между презентером и таской проходит узкий интерфейс, за которым спрятана реализация. View не знает, когда кнопка `disabled`, презентер не знает, откуда пришли данные: из HTTP, кэша или сокета. Пока интерфейс не меняется, стороны меняются независимо.

Модуль принимает только то, что использует (принцип разделения интерфейсов, ISP):

```ts
export const toggleFavorite = async (show: FavoriteMark) => { … };   // { id, isFavorite }
export type FavoriteStarProps = { show: Pick<ShowListItem, 'id' | 'name' | 'isFavorite'> };
```

Вызывающий передаёт объект целиком (`toggleFavorite(show)`, `<FavoriteStar show={show} />`): TypeScript сравнивает типы по структуре и пропускает лишние поля. Изменение остальных полей `Show` модуль больше не задевает. Компонент, который использует почти все поля объекта (`ShowResults` и `ShowsPage`), сужать незачем.

## Стор — самое чувствительное место

От стора зависят и таски, и презентеры, поэтому изменение стора бьёт по всему приложению. Два принципа:

1. **Минимум данных.** Перед тем как добавить поле, спроси: можно ли держать это в презентере? Загрузка, ошибка, данные одного экрана — локальное состояние презентера: таска возвращает данные, а не кладёт их в стор. В сторе только глобальное: то, что нужно в нескольких несвязанных местах (`count` избранного — шапка, оверлей, звёздочка).
2. **Минимум обращений.** Чем меньше модулей знают устройство стора, тем дешевле его менять. Стор — только состояние и селекторы, без запросов и логики. Устройство полей знают селекторы рядом со стором:

```ts
export const selectIsFavorite = (state: FavoritesState, { id, isFavorite }: FavoriteMark) =>
  state.overrides[id] ?? isFavorite;
```

Таски и презентеры читают через селектор, а не через `state.overrides[…]`.

## Контракт API и адаптеры

Контракт принадлежит серверу и является общим интерфейсом фронта и бэка. Типы контракта используются на фронте как типы предметной области, в том числе в пропсах.

Заранее типы не дублируем: псевдоним ничего не развязывает, а копия поле в поле — лишний код, который отключает проверку `tsc` между пакетами. Свой тип и маппер заводятся **в таске, когда форма ответа перестала совпадать с тем, что нужно фронту**: даты как `Date`, `snake_case`, обёртки, объединение нескольких запросов, чужой или публичный API.

На сервере контракт — внешняя граница, а доменные типы (`server/src/types/`) — ядро. Сторы и доменные таски зависят от `types/`, контракт их реэкспортирует и собирает из них ответы API. Изменение формы ответа не задевает сторы.

## Зачем

Читабельность: строка `fetchFavorites(signal)` в презентере понятна без перехода внутрь, как ссылка в статье Википедии. Независимость: задачу или баг часто закрывает правка одной таски. Всё это работает на цель архитектуры: меньше человеческих трудозатрат на создание и сопровождение системы.
