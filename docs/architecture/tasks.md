# Tasks: бизнес-логика

## Откуда

В «Чистой архитектуре» есть два похожих понятия:

- **бизнес-правила** — правила, которые делают или экономят деньги, даже если выполняются вручную (банк берёт процент за кредит);
- **варианты использования** (use cases, интеракторы) — бизнес-правила конкретного приложения: что вводит пользователь, что получает в ответ и какие шаги выполняет система.

То, что мы называем бизнес-логикой, — это варианты использования. В VIPER им соответствует буква **I** (Interactor). В Simple Architecture этот слой называется **Tasks**: пользователь просит приложение выполнить задачу (зарегистрироваться, купить, найти сериал).

## Что такое таска

- **Таска — обычная функция.** Принимает входные данные, выполняет шаги, возвращает результат. Может быть `async`.
- **Имя — глагол** в camelCase: `searchShows`, `filterShowsByGenre`, `logout`.
- **Одна таска — одна функция.** Внутри её можно разбить на более мелкие таски, но снаружи это вызов одной функции.
- **Никакого React.** Таска не импортирует `react*`, хуки, компоненты и презентеры. Если завтра View и Presenter перепишут на другой фреймворк, таски останутся как есть.
- **Побочные эффекты разрешены.** «Чистая» здесь значит независимая от фреймворка, а не чистая функция в смысле ФП. Таска ходит в сеть через `httpGet`, работает со сторами, принимает `AbortSignal`.

Критерий: если шаг можно описать в спецификации без слов «экран», «кнопка», «страница», это таска. Подписи, форматирование, выбор состояния экрана и пагинация относятся к презентеру.

## Форма

```
logic/tasks/
  countGenres.ts            # таска-файл: один именованный экспорт countGenres
  searchShows/              # таска не влезла в 120 строк
    index.ts                # только реэкспорт: export { searchShows } from './searchShows';
    searchShows.ts          # точка входа
    toShow.ts               # части таски
```

Таска может вызывать другие таски.

## Кто вызывает таски

- Презентер и его вспомогательные хуки: презентер знает, на какое событие какую таску вызвать. Это мост между UI и бизнес-логикой.
- Другие таски.

View (`.tsx`) таски не импортирует.

## Сеть

Есть один http-клиент `httpGet` (`src/services/http/`), обёртка над `fetch`. Отдельного слоя доступа к данным (`productApi`, репозиториев) нет: запрос данных — это таска.

```ts
export const searchShows = async (query: string, signal?: AbortSignal): Promise<Show[]> => {
  const results = await httpGet<TvmazeSearchResult[]>(`${TVMAZE_URL}/search/shows`, {
    params: { q: query },
    ...(signal && { signal }),
  });
  return results.map(({ show }) => toShow(show));
};
```

- Таска на границе переводит DTO в **свой тип** (`Show`). Дальше по приложению ходит только он, DTO знают только сетевые таски.
- Если тот же запрос нужен второй таске, он выносится в отдельную таску (`fetchShow`) по общему правилу переиспользования, а не в DAL.

### Почему без DAL

Плюсы: сценарий читается в одном месте, нет прослоек, которые только передают вызов дальше, а смена транспорта всё равно затрагивает одно место (`httpGet`).

Минусы: таска знает конкретный бэкенд и его формат, а при втором потребителе возможно дублирование. Первое смягчает маппинг в свой тип, второе — вынос общей таски. Направление зависимостей разбирается в будущих уроках.

## Entity и Router

- **Entity** (сущности) — данные из стора плюс методы их обновления. Эту роль играет стейт-менеджер. Таски обращаются к стору напрямую (`store.dispatch`, `store.getState`, `useStore.setState`), без посредников вроде redux-thunk и redux-saga.
- **Router** — навигация выполняется в презентере, а не в таске: что делать после успешного выполнения, зависит от среды (браузер, мобильное приложение), а не от бизнес-логики.
